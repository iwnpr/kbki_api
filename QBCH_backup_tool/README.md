# qbch-backup-tool

Служба восстановления данных **fallback-сценария** QBCH.

## Зачем нужна

`QBCH_api` при штатной работе сохраняет результат обработки запроса в **Redis**, а затем
отправляет уведомление в **Kafka**. Если любой из этих шагов не удался — Redis недоступен
или Kafka не приняла сообщение, — обработчик
[`QBCHProcessingCompleteHandlerV3`](../QBCH_api/QBCHProcessing/V3/StoreProcessingData/Event/QBCHProcessingCompleteHandlerV3.cs)
сохраняет данные запроса в backup-файл, чтобы результат обработки не потерялся.

Эта утилита разбирает такие файлы: доливает недостающее в Redis и Kafka и удаляет
обработанные файлы. Работает в фоне как служба, вмешательства оператора не требует.

## Как работает

Утилита с интервалом `BackupTool:IntervalSeconds` (по умолчанию 60 секунд) просматривает
каталог backup. Для каждого найденного файла:

1. **вычитывает** запись;
2. **проверяет в Redis**, есть ли данные по ключу `QBCH:{service}:{RequestId}`;
3. **доливает недостающее**:
   - ключа в Redis **нет** — значит падал Redis: утилита записывает данные в Redis, затем
     отправляет ключ в Kafka;
   - ключ в Redis **есть** — значит Redis отработал, а падала Kafka: утилита отправляет
     только уведомление, данные в Redis не трогает;
4. при **успехе удаляет** обработанный файл.

Проверка состояния Redis — это то, что позволяет одному и тому же файлу обслуживать оба
сценария сбоя.

Файл, который восстановить не удалось, остаётся на диске и будет обработан на следующем
проходе — отдельный запуск после устранения причины сбоя не нужен. Если проверить состояние
Redis не удалось (Redis всё ещё недоступен), запись считается необработанной: утилита не
делает ничего вслепую и, в частности, никогда не отправит уведомление о данных, которых в
Redis нет.

Запись в Redis идемпотентна: повторная обработка того же файла перезапишет те же поля
теми же значениями.

### Что именно восстанавливается

Поля redis-хэша, которые формирует `ConstructResultData` в API: `request_date_time`,
`request_certificate_thumbprint`, `response_date_time`, `response_guid`, `ip_address`,
`error_code`, `error_message`, `request_signed_data`, `request_xml`, `response_signed_data`,
`response_xml`, `validation_date_time`. В Kafka уходит сообщение с ключом `Null` и значением
`QBCH:{service}:{RequestId}` — так же, как его отправляет API.

> **Ограничение.** В backup-файле нет «сырых» данных сертификата (`request_certificate_data`),
> ошибок пакетного запроса (`package_error`), клиентского `request_id` и полей версии
> контракта (`api_version`, `contract_version`, `response_kind`, `schema_family`).
> Эти поля не записываются в файл и восстановлены не будут.

## Backup-файлы

Формат — один JSON-объект на файл, имя файла содержит идентификатор транзакции:

```
backup/{RequestId}.json
```

Двоичные поля (подписанный запрос, XML, тикеты) хранятся в Base64 — так `System.Text.Json`
сериализует `byte[]`. Читать содержимое глазами удобно так:

```bash
python3 -c "import json,base64,sys; d=json.load(open(sys.argv[1])); print(base64.b64decode(d['request']).decode('utf-8'))" backup/8f1c2e34-....json
```

### Где их искать

API создаёт подкаталог `backup` **рядом со своим исполняемым файлом**. Под IIS это
физический каталог сайта:

```
C:\inetpub\wwwroot\qbch_api\backup\
```

Полный путь пишется в лог API при каждом сохранении строкой
`Результат обработки сохранён в backup-файл ...`.

Учётной записи пула приложений нужны права на запись в этот каталог. Если публикация
настроена с удалением лишних файлов в месте назначения, каталог лучше вынести за пределы
сайта, иначе деплой снесёт необработанные записи.

## Сборка и зависимости

Проект входит в решение `QBCH_api.sln`, но **автономен**: у него нет `ProjectReference` ни на
один проект решения. Он запускается отдельно от API (в том числе на другой машине) и работает
с Redis и Kafka напрямую через `StackExchange.Redis` и `Confluent.Kafka`. Собирать и
выкатывать его можно независимо от API.

```bash
dotnet build QBCH_backup_tool/QBCH_backup_tool.csproj -c Release

# публикация под конкретную платформу
dotnet publish QBCH_backup_tool/QBCH_backup_tool.csproj -c Release -r win-x64 --self-contained
```

Формат ключа Redis, правила записи полей хэша (подписанные данные — сырыми байтами,
остальное — UTF-8 текстом) и формат сообщения Kafka продублированы внутри утилиты —
в `Services/RedisBackupStore.cs` и `Services/KafkaNotifier.cs`. Это цена автономности:
**при изменении этих правил в `Cache_lib`/`KafkaService_lib` их нужно синхронно поправить
и здесь**, компилятор об этом не предупредит.

## Конфигурация

Все настройки берутся **из собственных файлов утилиты**. Конфигурация веб-приложения не
читается и не требуется.

`appsettings.json` рядом с исполняемым файлом:

```json
{
  "ConnectionStrings": {
    "Redis": "10.10.100.84:6379,password=***,abortConnect=false"
  },
  "RedisCache": { "DBIndex": 0 },
  "KafkaService": {
    "BootstrapServers": "10.10.100.71:9092",
    "Topic": "RedisMessagesTopicv2"
  },
  "BackupTool": {
    "BackupDirectory": "C:\\inetpub\\wwwroot\\qbch_api\\backup",
    "IntervalSeconds": 60,
    "Target": "auto",
    "ServiceName": "dlrequest"
  }
}
```

| Параметр | Назначение |
| --- | --- |
| `ConnectionStrings:Redis` | строка подключения StackExchange.Redis |
| `RedisCache:DBIndex` | индекс БД Redis (по умолчанию `0`) |
| `KafkaService:BootstrapServers` | адрес брокера Kafka |
| `KafkaService:Topic` | топик уведомлений |
| `KafkaService:MessageTimeoutMs` / `RequestTimeoutMs` / `SocketTimeoutMs` | таймауты продюсера (необязательные) |
| `BackupTool:BackupDirectory` | каталог backup приложения |
| `BackupTool:IntervalSeconds` | период проверки каталога |
| `BackupTool:Target` | режим: `auto` / `redis` / `kafka` |
| `BackupTool:ServiceName` | redis-scope, часть ключа `QBCH:{service}:{id}` |

Источники конфигурации, каждый следующий переопределяет предыдущий:

1. `appsettings.json` рядом с исполняемым файлом;
2. `appsettings.{environment}.json` рядом с ним же (если указан `--environment`);
3. переменные окружения (`ConnectionStrings__Redis`, `KafkaService__BootstrapServers`, …);
4. переопределения `--define` (`-D`).

Относительный `BackupDirectory` разворачивается от каталога утилиты, абсолютный
используется как есть. Значение по умолчанию `backup` подходит только если утилита лежит
в одном каталоге с приложением; в остальных случаях указывайте полный путь.

> **Секреты.** Пароль Redis попадает в файл настроек, поэтому боевой
> `appsettings.{env}.json` не должен уезжать в репозиторий — храните его рядом с
> развёрнутым экземпляром или задавайте подключение переменными окружения. Передача
> через `-D` в проде нежелательна: строка с паролем останется в истории команд и будет
> видна в списке процессов.

## Запуск

Штатно утилита запускается без аргументов и работает бесконечно

Процесс не завершается сам и не управляется с клавиатуры. Остановка — средствами хостинга.

### Аргументы командной строки

| Опция | Описание |
| --- | --- |
| `-d, --backup-dir <путь>` | каталог с backup-файлами (перекрывает конфиг) |
| `-f, --file <путь>` | обработать конкретный файл (можно повторять); каталог не сканируется |
| `-t, --target <auto\|redis\|kafka>` | режим восстановления |
| `--service-name <имя>` | redis-scope |
| `-e, --environment <env>` | окружение для `appsettings.{env}.json` |
| `-D, --define <Ключ=Значение>` | переопределить параметр конфигурации |
| `-n, --dry-run` | ничего не отправлять и не удалять — только показать план |
| `--keep` | не удалять backup-файлы даже при успехе |
| `--stop-on-error` | остановить проход на первой ошибке (по умолчанию — продолжать) |
| `-v, --verbose` | подробный (Debug) вывод в консоль |
| `-h, --help` | справка |

### Режимы `--target`

- `auto` (по умолчанию) — решение по наличию ключа в Redis, как описано выше. Файл удаляется,
  только если успешны все нужные операции; в Kafka ничего не уходит, если запись в Redis
  не удалась. Если проверить Redis не удалось, файл остаётся на диске.
- `redis` — принудительная запись в Redis без проверки и без Kafka. Подключение к Kafka
  не требуется.
- `kafka` — принудительная отправка ключа в Kafka без проверки и без записи в Redis.
  Подключение к Redis не требуется.

Принудительные режимы нужны для нештатных ситуаций, например когда данные в Redis повреждены
и их надо перезаписать. В обычной работе достаточно `auto`.

### Коды возврата

| Код | Значение |
| --- | --- |
| `0` | показана справка (`--help`) |
| `2` | ошибка запуска или конфигурации |

При штатной работе утилита не завершается, поэтому кода «всё восстановлено» нет — итог
каждого прохода, в котором были файлы, пишется в лог строкой `Итог прохода: ...`.

## Развёртывание

1. Опубликуйте утилиту в отдельный каталог.
2. Заполните в `appsettings.json` подключения к Redis и Kafka (при первом развёртывании они
   пустые) и путь `BackupTool:BackupDirectory` к каталогу backup приложения.
3. Проверьте настройки одним запуском с `--dry-run --verbose`: утилита покажет каталог,
   найденные файлы и план по каждому — ничего не отправляя и не удаляя.
4. Зарегистрируйте её как службу и запустите.
5. Дальше вмешательство не нужно: файлы, появившиеся при сбое Redis или Kafka, будут долиты
   на ближайшем проходе.

Учётной записи, под которой работает утилита, нужны права на чтение и удаление файлов
в каталоге backup.

## Логирование

Логи пишутся в консоль и в файлы `logs/qbch-backup-tool-YYYYMMDD.log` рядом с исполняемым
файлом (ротация по дням, UTF-8). Настройка — в секции `Serilog` файла `appsettings.json`.
Файловый лог всегда ведётся на уровне `Debug` и служит журналом восстановления.

Полезные строки в логе:

| Строка | Что означает |
| --- | --- |
| `Каталог backup: ...` | путь, в котором утилита ищет файлы |
| `Запись {id}: данных в Redis нет — восстанавливаем данные и уведомление.` | сработал сценарий падения Redis |
| `Запись {id}: данные в Redis уже есть — переотправляем только ключ в Kafka.` | сработал сценарий падения Kafka |
| `Backup-файлы не найдены` | каталог пуст или указан неверно |
| `Итог прохода: ...` | сводка прохода, в котором были файлы |

## Диагностика

**Утилита пишет «Backup-файлы не найдены», хотя файлы есть.** Сверьте строку `Каталог
backup: ...` в логе утилиты с путём из лога API — почти всегда расходятся именно они.

**Записи не обрабатываются, в логе ошибки проверки ключа.** Redis недоступен для утилиты:
проверьте `ConnectionStrings:Redis` и сетевой доступ. Файлы при этом не теряются.

**В логе ошибка чтения/разбора файла на каждом проходе.** Файл повреждён (обрезан при
записи) — восстановить его нельзя, уберите его из каталога вручную.
